# ConnLab 项目 GPT‑6 Astra 使用指南

更新日期：2026-09-05。面向主要依靠 AI 开发 ConnLab 的项目负责人。

你负责说明业务目标和验收结果；Astra 负责理解代码、选择实现方案、修复、审查与验证。
日常任务不需要你安排角色、填写 Git SHA，或决定测试该调用哪个私有函数。

本指南是使用说明。项目执行规则仍只有 [AGENTS.md](../../AGENTS.md) 与
[详细流程](SOL_NATIVE_WORKFLOW.md)，任务状态由 [看板](../task_board.md) 保存。
不需要每次执行任务都重新阅读本指南。

## 1. 本版依据与适用范围

- 依据 OpenAI 的 [Astra 官方指南](https://developers.openai.com/api/docs/guides/latest-model)
  和 [Codex 最佳实践](https://learn.chatgpt.com/guides/best-practices)，以及当前仓库规则与测试脚本。
- 官方指出 Astra 更敏感地遵循技能和本地指令，可能更多询问澄清，也可能对小改动验证过多。
  因此本项目强调明确授权、简洁规则和按实际风险验证；下面的具体流程是 ConnLab 的工程选择。
- 用户提供的 [GPT‑5.6 共享指南](https://chatgpt.com/share/6a9b4f58-6964-83ec-a890-69697dcb3ef6)
  在编写时能显示标题，但正文读取超时。本版不是对该页面逐条核对后的改写，未假定其未读取内容。
- 这次升级的是开发协作说明，不是给 ConnLab 产品接入新的 AI API。
  `connlab_sol_task.py`、`sol_native` 和流程文件中的 SOL 名称是兼容标识，不会把模型切回 Sol。
  实际模型与推理强度以应用设置为准；Markdown 文件不负责切换模型。

## 2. 最常用的任务写法

简单任务可以只写一句：

> 把文件列表默认改为修改时间倒序，最新文件在最上面，保留手动排序。请直接完成并验证。

稍复杂的任务补充四项即可：

> 请在 ConnLab 实现【目标】。用户现在【操作过程与问题】，希望【完成后的行为】。
> 相关页面、文件或例子是【上下文】。需要保留【业务边界】。
> 完成标准是【我能观察到的结果】。请自行定位代码、实现、自审和验证，完成后交付。

你不确定技术方案时，可以直接说“不懂技术，由你根据现有代码决定”。
如果业务含义也未确定，用实际输入与期望输出举例，Astra 先把关键选择说清楚。
普通命名、模块位置、测试方式、局部修复无需再次批准。

## 3. 三种任务由 AI 判断

| 任务 | 例子 | 执行方式 |
| --- | --- | --- |
| 极简 | 默认排序、明确的文案或小范围文档修改 | 直接修改、自审、定向检查、提交和交付 |
| 普通 | 新增已有边界内的业务功能，修改多个相关模块 | 紧凑计划与开发连续完成，聚焦审查，最后一次适度完整验证 |
| 高风险 | 实际数据库迁移、权限安全、权威文件写入、破坏性操作、大范围架构变更 | 保留独立 Planner、Developer、Reviewer、QA、Integrator 上下文，自动交接 |

复杂度与风险不同：文件多不自动要求 worktree；真正的迁移风险也不会因修改行数少而消失。
worktree 根据隔离需求选择。普通任务的聚焦审查可以由同一代理独立进行一轮检查，
但必须标为同代理审查，不能称为独立 Reviewer。高风险独立角色需要真实的独立上下文。

正常过程是“提出需求 → AI 交付 → 你验收后说关闭”。无需重复批准日常 Plan 或测试命令。
交付后发现同范围问题，直接反馈，AI 使用现有 `Revise` 继续同一任务。
当前 WIP=1；未关闭的活动任务不会因为换窗口或切模型自动结束。

## 4. 技能怎样合理使用

技能提供专业方法，不能新增业务范围、第二套审批链或重复角色。

| 方法 | 适用情况 | 合适粒度 |
| --- | --- | --- |
| diagnosing-bugs | 难复现、异常、性能退化 | 证据、定位、修复与验证；Windows 硬件故障另行诊断 |
| tdd | 有实际行为变化、存在公开测试边界 | 按完整行为切片；同一行为的相关用例可以合并，保留有效 RED/GREEN |
| code-review | 实质改动或明确要求审查 | 检查需求与代码质量，不额外建立一套 Review 流程 |
| codebase-design | 模块边界、耦合、重构 | 帮助选择职责边界，不强制全面重构 |
| grilling | 会显著改变业务结果的未解选择 | 只问影响结果的关键业务问题，不把技术决策转给用户 |
| 浏览器验证 | 可见交互、完整页面路径 | 检查受影响流程；不用每次打开所有页面 |

对可逆、低影响的小改动，检查现有行为通常足够；不为源码文字、私有变量名和任意行数写新测试。
本项目的 TDD 粒度由当前 AGENTS.md 约定，通用技能的一测试一循环偏好不应制造额外工具往返。
全局 skills 本次没有删除或改写；其他项目仍按各自规则使用它们。

如果技能真的导致暂停，Astra 应说明具体文件、原文要求及实际缺失条件，
并区分明确规则与自己的推断。用户当前授权不能被通用技能反复要求重批；
系统权限与工具限制仍需按实际边界处理。

## 5. 验证以可信交付为目标

开发过程用小范围测试快速反馈。实质修改完成后先审查、修复已知问题，
再在最终代码状态运行所需验证。只有新修改、失败或未解风险才扩大或重复检查。
后续改了相关实现或测试，应重新验证受影响部分，不能继续引用旧结果为新状态背书。

当前仓库根目录的验证入口：

```powershell
# 普通完整门禁：隔离 Office 的 Python 测试 + 前端测试 + 构建
.\scripts\run_tests.ps1

# 按实际影响选择；不要求每次全部执行
.\scripts\run_tests.ps1 -Suite Python
.\scripts\run_tests.ps1 -Suite Frontend

# 仅在需要真实 Office 集成验收且环境具备条件时执行
.\scripts\run_tests.ps1 -Suite Office
```

脚本的 Python 入口为 `py`，运行前由 AI 核对实际解释器和依赖，不根据历史环境路径猜测。
前端测试和构建在本 Windows 主机顺序执行，避免同时启动 esbuild。
已知权限不足时应先申请完整命令所需的具体权限，不先制造一次 EPERM/index.lock 失败。

对“既存失败”，必须有基线证据才能下结论；仅凭失败文件未修改不能证明与本次无关。
已通过的定向检查、失败的完整套件、未运行的 Office 集成验证应分别如实报告。
不能为绿色结果放宽业务断言，也不能把同一代理自审包装成独立审查。

## 6. ConnLab 的业务边界

ConnLab 是离线优先、Windows 为主的连接器实验室工作台。Project 管生命周期与追溯，
Matrix 管测试执行映射。报告、记录和费用文件消费已确认业务事实。

公共盘 LTR 和已批准 Word/Excel 模板保留现有权威；模型升级不授权替换它们。
SQLite、前端状态、派生工作簿的职责以当前实现与 [项目上下文](../PROJECT_CONTEXT.md) 为准。
Office/文件操作经过现有适配器，释放 COM、句柄和进程；不要把系统权限或硬件问题当成业务逻辑修复。

命名、测试和局部结构选择可自主决定；新依赖、跨模块抽象和兼容层必须有当前任务的实际需要。
与目标无关的历史债务简要记录，不夹带到功能任务中修复。

## 7. 可以直接复制的协作指令

**故障修复：**

> 在【页面】执行【操作】时出现【错误】，期望【结果】。请定位并修复根因，保留现有有效功能，验证后交付。

**只要方案：**

> 请先理解相关代码，给出实现方案、业务选择和验收口径。本轮只分析，不修改文件。

**中途补充：**

> 这是当前任务的补充：【要求】。复用已经完成的工作，只调整受影响部分。

**中断恢复：**

> 继续当前活动任务，从 board、Git 和已有证据恢复，复用已完成步骤。

**观察另一个任务：**

> 观察任务【任务链接】的动作和耗时，只记录分析。区分精确命令耗时与估计阶段时间，不发送干预消息。

**同范围验收反馈：**

> 验收发现【具体问题】，仍属于当前目标，请继续当前任务修复并验证。

**最终关闭：**

> 关闭。

## 8. 设置、交付与后续优化

推理强度按任务难度选择：明确小改动可用 Low，普通开发用 Medium/High，
困难排错和复杂架构再提高。保持用户已选设置，实际比较效果后再调整，不默认最高档。
模型 API 参数与 Codex 界面设置不是同一配置入口；本指南没有改全局模型、账号或插件配置。

最终交付应回答：做成了什么、在哪里、怎样验证、尚有什么限制、现在是否等待关闭。
详细日志保留可追溯位置，正文不用重复全部 Plan、board JSON 和角色声明。
若用户要求效率记录，利用已有 turn、命令和测试时间；不增设遥测系统，不编造精确阶段秒数。

以后优化依据重复出现的实际问题：定位走弯路、同一权限失败、无价值测试重复、材料重复读取。
先消除这些成本，再决定是否需要更多技能或并行代理。提高模型能力不等于取消业务边界和验证。
