## Goal

Create the backend foundation for versioned Confirmed Fee authority records.

Confirmed Fee is not an Excel file and not a project output ledger entry. It is the operator-approved pricing authority snapshot that later tasks can use to decide whether package preparation may proceed.

V1 contract:

- Confirmed Fee is created from the latest saved Fee Evaluation pricing draft from TASK_301.
- The saved pricing draft must be current for the active Confirmed Matrix id, active Confirmed Matrix revision, and active fee rule version id.
- The confirmation request must include `expected_pricing_draft_edit_id`; the service loads the latest saved pricing draft and rejects confirmation if the id does not match.
- The confirmation command stores caller-provided totals as the pricing summary snapshot.
- The confirmation timestamp is generated by the backend service clock, not supplied by the API caller.
- TASK_308 does not recalculate pricing formulas, does not read/write Excel, and does not add frontend UI.
- Operator-facing `Confirm Fee` UI and stale presentation are TASK_309.

## Current Code Context

Relevant existing pieces:

- `FeeEvaluationPricingDraftPersistenceService` saves and loads edited Fee Evaluation values bound to `project_id`, `confirmed_matrix_id`, `confirmed_revision`, and `fee_rule_version_id`.
- `FeeEvaluationPricingDraftEditRepository` stores one current saved pricing draft per project/Matrix/rule tuple.

- No Confirmed Fee domain model, repository, service, or API exists yet.

## Key Design Decisions

### Confirm Source

TASK_308 confirms only a saved current pricing draft. It does not accept unsaved UI row edits directly.

Reason: Confirmed Fee is an authority record. The preview/export flows may use transient UI state, but authority confirmation should depend on a structured, reloadable saved draft. TASK_309 can save current page edits first, then call the TASK_308 confirm endpoint.

### Totals Source

V1 confirmation request includes the displayed totals:

- `testing_fee_total`
- `working_hours`
- `lab_manpower_cost`
- `external_cost`
- `grand_cost`

The backend stores these totals as a snapshot and validates that they are present numeric strings or numbers. It does not recompute the formulas from rows in TASK_308. A backend totals calculator can be a later controlled task if needed.

The request also includes `expected_pricing_draft_edit_id`. This protects the authority snapshot from a race where totals were calculated from one saved draft but the latest persisted pricing draft changed before confirmation.

### Stale Semantics

A Confirmed Fee version is current only when all three values still match current project state:

- active Confirmed Matrix id
- active Confirmed Matrix revision
- active fee rule version id

The service read model should expose `status = current | stale | missing`.

### Versioning

Each confirmation creates an immutable version row.

V1 revision rule:

- first confirmation for a project creates `confirmed_fee_revision = 1`
- each later confirmation for the same project creates `max(revision) + 1`
- latest by project is ordered by revision descending, then confirmed timestamp/id

Do not overwrite prior Confirmed Fee versions.

### Pricing Effective Date

V1 persists `pricing_effective_from = None` unless the existing fee/pricing context already exposes a value without adding a new repository lookup. TASK_308 must not add a Project/application-form dependency solely to derive this field.

### Application Service

Create `backend/application/confirmed_fee_version_service.py`.

Ports:

- `ConfirmedFeeVersionStore`
  - `create(...)`
  - `get_latest_by_project(...)`
  - `list_by_project(...)`
- `FeeEvaluationPricingDraftLoader`
  - can be the existing `FeeEvaluationPricingDraftPersistenceService.load(project_id)`

Commands/results:

- `ConfirmFeeVersionCommand`
  - `project_id`
  - `confirmed_by`
  - `expected_pricing_draft_edit_id`
  - `summary`
  - `confirmation_note: str | None = None`
- `ConfirmedFeeVersionReadResult`
  - `status`
  - `current_confirmed_matrix_id`
  - `current_confirmed_revision`
  - `current_fee_rule_version_id`
  - `latest_confirmed_fee`

Service behavior:

1. Load current Fee Evaluation pricing draft through TASK_301 service.
2. If load status is `missing`, fail with actionable error: save Fee Evaluation pricing before confirming.
3. If load status is `stale`, fail with actionable error: refresh/re-save Fee Evaluation pricing for current Matrix/rule version.
4. If `saved_snapshot.draft_edit_id != expected_pricing_draft_edit_id`, fail with conflict: the Fee Evaluation draft changed after the totals were prepared.
5. Validate summary fields are present and numeric enough for a snapshot.
6. Generate `confirmed_at` using the service clock. Unit tests may inject a fixed clock seam, but the production API must not accept `confirmed_at`.
7. Serialize the pricing draft edited values using existing `edited_values_to_json(...)`.
8. Create a new immutable Confirmed Fee version with next revision.
9. Return the created version.

Read behavior:

1. Load current Fee Evaluation pricing draft context using TASK_301 service.
2. Load latest Confirmed Fee by project.
3. Return `missing` if none.
4. Return `current` only if latest Confirmed Fee binding matches current context.
5. Return `stale` otherwise.

## Error Handling

Use explicit errors in the application service, for example:

- `ConfirmedFeePricingDraftMissingError`
- `ConfirmedFeePricingDraftStaleError`
- `ConfirmedFeeSummaryValidationError`

Route mapping:

- missing active Confirmed Matrix from pricing draft load: `404`
- missing saved pricing draft: `409`
- stale saved pricing draft: `409`
- expected draft id mismatch: `409`
- invalid summary payload: `422`

Messages must be operator-actionable and must not expose SQLAlchemy internals.

## Risks And Mitigations

- Risk: Confirmed Fee is confused with generated Fee Form file.
  - Mitigation: table/service names use `confirmed_fee`, not `fee_form`; no Office gateway or output-record dependency.
- Risk: stale checks ignore fee rule version.
  - Mitigation: binding tuple always includes `fee_rule_version_id`; service tests cover stale rule version.
- Risk: UI totals and backend snapshot diverge.
  - Mitigation: TASK_308 stores caller-provided totals as immutable snapshot and requires `expected_pricing_draft_edit_id`; TASK_309 must call confirm with the saved draft id used to prepare the displayed totals.
- Risk: saved draft payload changes shape later.
  - Mitigation: snapshot stores stable JSON through existing TASK_301 serializer and keeps versioned Confirmed Fee rows immutable.
