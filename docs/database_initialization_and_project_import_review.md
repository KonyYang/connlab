# 数据库初始化修复与 Add Existing Project 评估

日期：2026-11-12。范围：数据库缺陷修复；依据用户截图评估导入流程，并继续修复导入阻塞提示与下一步操作。未读取实际 LTR 工作簿，未对真实项目文件、数据库执行验证写入。

## 数据库问题

项目列表同时读取 registry、library members、legacy projects、trash、history，任一请求失败都会显示通用的部分加载错误。日志已记录 `table ltr_records_new already exists`。

根因有两层：SQLite 索引检测没有排除 partial unique index，将已完成迁移的 LTR 表误判为旧结构；API 的 lru_cache 只缓存已完成结果，不能阻止首次并发请求多次运行 init_db。迁移应只针对旧的无条件唯一约束；引擎初始化需在缓存查询外串行化，失败释放资源并允许重试。

验收：旧结构升级保留数据和唯一性规则；对已升级结构重复初始化不重建 LTR 表；并发首次请求共享完成初始化的引擎；失败不缓存、释放失败引擎且可重试；缓存清除兼容既有调用。测试使用合成 SQLite 与临时目录。

边界：本次解决单服务进程内的首次请求竞争，不宣称跨进程迁移互斥。不会自动删除或恢复历史遗留临时表。实际运行数据的修复需要单独检查与授权。

## Add Existing Project 当前链路

1. 检查默认保存位置，选择源项目目录，扫描项目身份或快照。
2. 生成接收计划。对需要从既有 LTR 接管的编号，读取配置的权威工作簿进行验证；目录名称本身不能授权接管。
3. `ready` 项进入接收路径，已存在项打开现有项目，冲突项等待决策，`unavailable` 项阻止执行。
4. 部分普通 ready 项和快照会自动接收；带 authority_status 的新 LTR 接管需确认。真正的复制发生在接收阶段，后端会再次验证接收条件。
5. 完成后打开项目或展示批次结果，失败与中断保留恢复入口。

代码依据：`frontend/src/features/project-library/ProjectLibraryImport.tsx`、`ProjectImportReviewList.tsx`、`ProjectImportDecision.tsx`；`backend/application/project_library/service.py`、`existing_ltr_adoption.py`。

## 初次评估：截图结论与设计问题

用户截图中 DL-2026-08-079 的检查结果为“在当前配置的 LTR 工作簿中未找到”。这与数据库并发异常是两条不同路径。`target_path` 是预先计算的计划位置，不证明文件已经写入 D:\ConnLabProjectsDev。单个 unavailable 项不可选择，确认区因此不会渲染；没有保存按钮符合当前门禁，但界面解释不足。

| 场景 | 当前表现 | 评估与建议 |
| --- | --- | --- |
| 权威编号检查失败 | 关键原因在 Details，外部仅说重新选择 | 应直接显示具体阻塞原因，并提供核对编号、当前工作簿配置与重新检查的明确路径；重选同一目录通常无效 |
| 检查失败仍显示路径 | 标题为 Save location | 容易被理解成已保存。应标识为计划位置、尚未导入，或在阻塞时隐藏 |
| 单项不能导入 | 无 Confirm Import | 不应添加绕过校验的保存按钮；应直接说明尚未复制、需要先解决哪项条件 |
| 不同来源的成功路径 | 有些自动接收，有些要求确认 | 选择目录与执行导入的含义不统一。后续需统一可预期的确认语义，并避免自动复制产生意外 |
| 重复项目与冲突 | 打开已有项目或要求决策 | 方向合理，应继续保护原文件和已有人工编辑，不能用重试覆盖已有成果 |
| 实际结果 | 根据批次展示成功、失败、待处理 | 结果应以持久化事实为准，计划路径不能作为成功证明 |

合理边界：校验失败时不复制，保留源文件，执行前复查。需要讨论的业务选择：权威工作簿确实缺少编号时，是否允许仅保存文件而不接管为正式项目；本次不改变该规则。

## 后续 UI 验收建议

使用隔离目录和合成工作簿覆盖：已登记新项目、缺失 LTR、工作簿不可用、已存在相同项目、同号不同副本、有效快照、损坏快照、目标冲突、接收中断与恢复。逐项检查阻塞原因是否直接可见、用户能否判断是否已复制、下一步是否可执行、重试是否保护已有文件。再检查窄屏长路径、键盘焦点与弹窗返回。

限制：本次没有对截图项目重新执行真实导入，也没有验证其真实工作簿内容。因此无法断言该编号在业务上不存在，或完整导入流程已经通过实机验收。上述 UI 问题为当前代码及所提供截图支持的评估，后续提示修订见下节；不改变这些业务规则。


## 继续修复：导入阻塞提示

用户授权的后续范围为提示、计划位置标签、有效下一步操作及回归测试。使用现有 `item.warnings` 展示具体原因，不解析错误文案决定业务类型，也不修改后端的资格校验、自动接收或确认门禁。

- 普通接收计划为 unavailable 时，在折叠详情外显示 Not imported 与去重后的具体原因；详情不重复同一组原因。缺少原因时提供可操作的通用降级说明。
- 尚处于预览的目标使用 Planned save location；已存在项目使用 Existing location，避免混淆计划与实际成果。
- 通过已有 Settings 回调提供配置入口。当前应用会关闭导入弹窗再打开 Settings；修改配置后需返回 Projects 重新选择目录，不承诺保留弹窗。
- Check and Continue 复用既有检查流程。普通可接收来源可能按原规则继续自动导入，因此按钮不声称只读；校验恢复成功的权威 LTR 接管仍需 Confirm Import。
- 保留 Change Folder、Cancel 和忙碌时的操作限制；不提供绕过 LTR 检查的保存动作。

修订验收：原因无需展开 Details 即可见；阻塞项目明确尚未导入；计划路径标签准确；重复检查失败无接收请求；Settings 能导航；LTR 检查恢复后仍等待确认；已有自动导入与重复项目打开行为保持兼容。组件测试使用模拟 API，浏览器使用独立端口并拦截所有 API 请求，不连接真实业务后端。验证结果由任务看板记录。
